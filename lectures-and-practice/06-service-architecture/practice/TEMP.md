## 1. Суть задания

Есть работающий сервис объявлений в одном `main.go`. Нужно **отрефакторить его без изменения поведения** (ТЗ в README) до слоистой архитектуры, как `after/` в репозитории lecture6-architecture. Затем открыть PR и в описании честно указать, какие из 5 пунктов закрыты.

Оценка (2 балла = 5 × 0.4), смотрят дифф глазами:

| Пункт | Что должно быть видно в диффе |
|---|---|
| Слои | handler / service (usecase) / storage в разных пакетах, граница видна по импортам |
| Богатые модели | модель сама проверяет инварианты и переходы статусов |
| Ошибки по слоям | доменные ошибки + явный перевод в HTTP-статусы в транспортном слое |
| Порты и адаптеры | интерфейсы для хранилища и модерации; бизнес-логика не знает про `map` и `http.DefaultClient` |
| DDD | доменная модель отдельно от модели хранения (не «одна структура на всё») |

## 2. Что зафиксировано ТЗ (поведение, которое нельзя менять)

**POST /listings** — тело `{title, price, photo_url, seller_id}`. Порядок проверок важен:
1. битый JSON → 400 (пустое тело);
2. `price <= 0` → 400 `price must be positive`;
3. `photo_url` пуст после `TrimSpace` → 400 `photo is required`;
4. `price > 10_000_000` → 400 `price looks suspicious`;
5. создать со статусом `pending`, сохранить, позвать модерацию;
6. модерация вернула HTTP 200 → `approved`; ошибка сети → остаётся `pending`; любой другой статус ответа → тоже `pending`;
7. ответ 201 `{"id":..., "status":...}`.

**GET /listings/{id}** — нечисловой id → 400 (пустое тело); не найдено → 404 (пустое тело); иначе 200 и объявление целиком.

**PATCH /listings/{id}/price** — порядок: id невалиден → 400; битый JSON → 400; `price <= 0` → 400 `price must be positive`; не найдено → 404; статус `rejected` → 409 `cannot update rejected listing`; успех → 200 и объявление.

### Тонкие места (легко сломать при рефакторинге)

- **JSON-формат GET/PATCH.** Сейчас `storedListing` кодируется без тегов, значит ключи в ответе — `ID`, `Title`, `Price`, `PhotoURL`, `SellerID`, `Status`, `CreatedAt`. Если вы заведёте DTO ответа с тегами `json:"id"` — поведение изменится. Либо сохраните те же ключи, либо осознанно отметьте это в PR.
- `http.Error` добавляет `\n` в конец тела и ставит `Content-Type: text/plain`. Сообщения ошибок должны остаться теми же.
- В POST ответ пишется без `Content-Type: application/json` (в GET/PATCH — с ним). Мелочь, но «не менять поведение» формально включает и это.
- Запрос в модерацию: `POST` на `http://moderation.internal/check` с телом `{"listing_id":<id>}`, `Content-Type: application/json`, с контекстом запроса. Сначала объявление сохраняется, потом идёт модерация. Если модерация одобрила, статус меняется на `approved` (в текущем коде — только в памяти указателя).
- Комментарий к правилу №3 говорит «сразу отклоняем», но код возвращает 400, а не создаёт `rejected`. Верно то, что делает код.
- `nextID` и `db` без мьютекса — гонка данных при параллельных запросах. Реальный репозиторий с map должен быть защищён `sync.Mutex`/`RWMutex`. Это улучшение, не изменяющее поведение.
- `findByID` с `*sql.DB` в хендлерах не используется. Это учебный пример для репозитория: показывает, где нужно перевести `sql.ErrNoRows` в доменную `ErrNotFound`.

## 3. Рекомендуемая целевая структура

```
practice/
├── cmd/server/main.go            # composition root: сборка зависимостей, запуск
└── internal/
    ├── domain/
    │   ├── listing.go            # Listing (богатая модель), Status, конструктор NewListing, методы
    │   └── errors.go             # ErrNotFound, ErrInvalidPrice, ErrPhotoRequired, ErrSuspiciousPrice, ErrRejectedListing
    ├── service/
    │   ├── listing.go            # ListingService: Create, Get, UpdatePrice
    │   └── ports.go              # интерфейсы Repository, Moderator (объявляем там, где ПОТРЕБЛЯЮТСЯ)
    ├── storage/
    │   └── memory/repo.go        # адаптер: map + mutex, своя storedListing + мапперы toDomain/fromDomain
    ├── moderation/
    │   └── http.go               # адаптер: HTTP-клиент в moderation.internal
    └── transport/http/
        ├── handler.go            # разбор запроса, вызов сервиса, ответ
        └── errors.go             # errors.Is(err, domain.ErrX) → HTTP-статус
```

Правило зависимостей: `transport → service → domain`; `storage` и `moderation` реализуют интерфейсы из `service` и импортируют `domain`. `domain` не импортирует ничего из проекта. `main` — единственное место, знающее обо всех конкретных типах.

Тесты: `service` с fake-репозиторием и `fakeModerator`, который возвращает «отклонено», — так проверяется правило №4 (409), которое `curl`-ом не воспроизвести.

4. **Адаптеры** (15 мин): in-memory репозиторий (с мьютексом, генерацией ID, переводом «нет в map» → `domain.ErrNotFound`), HTTP-модератор.
5. **Сервис** (15 мин): `Create` (создать → сохранить → модерация → при успехе `Approve` и `Update`; при ошибке модерации — оставить `pending`), `Get`, `UpdatePrice`.
6. **Транспорт** (15 мин): хендлеры + единая функция `writeError(w, err)` с `errors.Is` → 400/404/409; неизвестная ошибка → 500, без утечки внутренностей.
7. **main + PR** (10 мин): сборка зависимостей, ручная проверка, PR с честной отметкой по 5 пунктам.

## 5. Теория

### 5.1 Слои (layered / clean architecture)

Идея: разделить код по **причинам изменения**. Транспорт меняется, когда меняется протокол (HTTP → gRPC), бизнес-логика — когда меняются правила, хранилище — когда меняется БД. Если всё в одной функции, любое изменение трогает всё и ничего нельзя проверить изолированно.

- **Transport/handler** — только разбор входа (JSON, path-параметры), вызов сервиса, формирование ответа и перевод ошибок в статусы. Никаких бизнес-правил.
- **Service/usecase** — оркестрация сценария: «создать → сохранить → спросить модерацию → обновить статус». Знает про порты, не знает про HTTP и SQL.
- **Domain** — сущности и правила. Не зависит ни от чего.
- **Infrastructure/adapters** — БД, внешние HTTP-клиенты.

**Правило зависимостей:** стрелки импортов идут внутрь, к домену. Внутренние слои не знают о внешних. В Go это проверяется буквально по `import` — отсюда фраза «граница видна по импортам». Пакеты в `internal/` не импортируются снаружи модуля.

Антипаттерны: хендлер, ходящий в БД; сервис, возвращающий `http.StatusX`; домен с `json`-тегами и `sql`-типами; «god-пакет» `utils`/`models`.

### 5.2 Богатые и анемичные модели

- **Анемичная** модель — структура с публичными полями, вся логика снаружи (сейчас `storedListing`). Любой код может записать `listing.Status = "banana"` или `listing.Price = -5`.
- **Богатая** модель — данные плюс поведение. Инварианты защищены: поля приватные (или недостижимые для обхода), создание только через конструктор `NewListing`, изменения только через методы (`ChangePrice`, `Approve`, `Reject`), которые возвращают ошибку при нарушении правил.

Что это даёт: правило «rejected нельзя редактировать» живёт в одном месте (`ChangePrice`), а не в хендлере; невозможно создать невалидный объект; правило тестируется без HTTP.

В Go:
- `type Status string` + константы `StatusPending/Approved/Rejected` — типобезопасный enum (ограничение значений достигается конструктором и методами, сам тип этого не гарантирует);
- приватные поля + геттеры (`l.Price()`), либо экспортируемые поля, но запись только через методы (договорённость). Для оценки лучше приватные поля;
- для восстановления объекта из хранилища нужен отдельный конструктор вроде `Restore(...)`, который не запускает бизнес-валидацию «создания»;
- конструктор возвращает `(*Listing, error)`.

### 5.3 Ошибки по слоям

Каждый слой говорит на **своём** языке ошибок, а на границе переводит:

- **Хранилище:** `sql.ErrNoRows` / «нет ключа в map» → `domain.ErrNotFound`. Иначе сервис и хендлер вынуждены знать про `database/sql` — утечка деталей реализации. Если заменить БД, сломается всё вышестоящее.
- **Домен/сервис:** sentinel-ошибки (`var ErrNotFound = errors.New("listing not found")`) или типизированные ошибки. Проверка через `errors.Is` / `errors.As`, а не `==` и не сравнением строк.
- **Транспорт:** единственное место с таблицей «доменная ошибка → HTTP-статус»:
  - `ErrInvalidPrice`, `ErrPhotoRequired`, `ErrSuspiciousPrice` → 400 (с тем же текстом сообщения);
  - `ErrNotFound` → 404;
  - `ErrRejectedListing` → 409;
  - всё остальное → 500, без подробностей клиенту (подробности — в лог).

Оборачивание: `fmt.Errorf("get listing %d: %w", id, err)` добавляет контекст и сохраняет возможность `errors.Is`. Сообщения 400/409 должны остаться прежними — их берём из текстов в ТЗ (сообщение клиенту ≠ `err.Error()` внутренней ошибки, если вы добавили контекст через `%w`; лучше маппить явно).

Отдельно: недоступность модерации — **не ошибка запроса**. Сервис должен поймать её и оставить `pending`, а не пробрасывать наружу.

### 5.4 Порты и адаптеры (hexagonal architecture)

- **Порт** — интерфейс, который описывает, что бизнес-логике нужно от внешнего мира: `Repository`, `Moderator`.
- **Адаптер** — конкретная реализация порта: `memory.Repository`, `moderation.HTTPClient`, позже `postgres.Repository`.
- Бизнес-логика зависит от интерфейса (dependency inversion), реализации подставляются в `main` (dependency injection через конструктор: `service.New(repo, moderator)`).

Go-идиомы:
- «Принимай интерфейсы, возвращай структуры»;
- интерфейс объявляется **на стороне потребителя** (в пакете `service`), а не рядом с реализацией; он маленький (1–3 метода);
- в интерфейсе порта нет типов адаптера (`*sql.DB`, `*http.Response`) — только доменные типы и `context.Context`;
- тест-дубли: handwritten fake (`fakeModerator`, возвращающий «rejected») проще и нагляднее моков.

Модерация как порт: удобно, чтобы адаптер сам переводил «HTTP 200 / ошибку сети / иной статус» в доменный результат (например, `approved` / `unavailable` / `not approved`), чтобы HTTP-коды не протекали в сервис. Адрес URL — параметр конструктора адаптера, а не глобальная переменная. Таймаут для HTTP-клиента лучше задать (по умолчанию `http.DefaultClient` ждёт бесконечно).

### 5.5 DDD и границы контекста (в объёме этого задания)

- **Сущность (Entity)** — объект с идентичностью (`Listing`, ID).
- **Инвариант** — условие, которое всегда должно быть истинным для объекта (`price > 0`, нельзя менять `rejected`).
- **Агрегат** — группа объектов, изменяемых как единое целое через корень; здесь `Listing` — и корень, и весь агрегат. Все изменения идут через его методы.
- **Репозиторий** — абстракция «коллекции агрегатов»; хранит и достаёт целиком агрегаты, скрывая способ хранения.
- **Ubiquitous language** — имена в коде совпадают с языком бизнеса (`Approve`, `Reject`, `ChangePrice`, а не `SetStatus("approved")`).
- **Ограниченный контекст** — у одного понятия в разных частях системы разные модели. Модерация — другой контекст; из неё нам нужен только вердикт, поэтому в домен объявлений не тащим её структуры.

Главный практический вывод для задания: **не одна структура на всё.** Три разные модели:
1. `domain.Listing` — бизнес-инварианты, никаких тегов и деталей хранения;
2. `storedListing` (или `listingRow`) внутри адаптера хранилища — как оно лежит (поля, теги `db`);
3. request/response DTO в транспортном слое — как это выглядит по HTTP.

Между ними — явные мапперы (`toDomain`, `fromDomain`, `toResponse`). Это больше кода, но каждая модель меняется независимо.
